# 1. MANDATORY ARCHITECTURAL PRINCIPLE — NATIVE FIRST

The most important requirement is:

**ALWAYS prefer native WordPress and WooCommerce interfaces, navigation structures, components and existing capabilities. Extend existing functionality before creating new functionality.**

Follow this decision hierarchy:

1. Reuse an existing native WordPress/WooCommerce feature.
2. Extend the native feature through officially supported APIs, hooks, filters, components or extension points.
3. Create a custom administrative screen inside the most relevant existing native menu.
4. Create an independent top-level administrative menu only when no appropriate native location exists and the decision is documented.

Do not create a parallel administrative system.

Do not create a separate dashboard that duplicates native WooCommerce functionality.

Do not reinvent products, orders, customers, coupons, tax configuration, shipping methods or payment settings when WooCommerce already provides appropriate infrastructure.

## Required menu organization

### WooCommerce
- Orders, including expanded order statuses and operational workflows.
- Customers, including store credit and relationships.
- Analytics and accounting reports.
- Coupons and promotions, using the existing WooCommerce/Marketing interface where available.
- Payments, shipping, tax and checkout configuration.

### Products
- All Products.
- Categories and attributes.
- Inventory / Stock Management.
- Bulk Inventory and Lots.
- Production Orders / Fractioning.
- Suppliers.
- Customs Classification / HS Codes.

### WordPress Users
- Administrative accounts.
- Permissions and capabilities.
- Relevant contact information.

### WordPress / WooCommerce Settings
- Sales channels and sites.
- Email account integrations and templates.
- Countries, tax, shipping and payment rules.
- Integration settings.

Other modules must be positioned in their most appropriate existing administrative section.

**Example:** Inventory Management belongs under `Products → Inventory`, not under a new top-level `Inventory Management System` menu.

Custom database tables are permitted and encouraged for complex transactional functionality. However, custom database architecture does not justify creating redundant administrative interfaces.

Do not modify WordPress or WooCommerce core files.

Preserve compatibility with WooCommerce HPOS, current supported APIs, WordPress capabilities and relevant WooCommerce data stores.

Avoid direct manipulation of WooCommerce order tables when supported CRUD APIs are available.

2. Is the native interface being reused?

|---|---|---|---|---|---|

Classify each module as:

- COMPLIANT
- PARTIALLY COMPLIANT
- NON-COMPLIANT

## A3. Existing functionality preservation

Before refactoring:

- Identify existing user workflows.

- Reuse WooCommerce customer accounts rather than creating parallel customer identities.
- Consolidate duplicate configuration screens into WooCommerce Settings.
- Replace unsupported database modifications with supported CRUD/data-store access.

When replacing interfaces, preserve their business logic and stored data.

# 9. ENGINEERING RULES

## Code quality

- Use maintainable PHP and TypeScript.
- Follow WordPress and WooCommerce coding standards where applicable.
- Apply separation of responsibilities.
- Avoid giant monolithic plugins.
- Avoid redundant custom functionality.
- Use dependency injection where it improves testability.
- Document non-obvious business rules.
- Prefer supported public APIs.

## Security

- Validate and sanitize input according to context.
- Escape output.
- Use capabilities and authorization checks.
- Use nonces where appropriate.
- Protect administrative and REST endpoints.
- Apply least privilege.
- Protect customer information.
- Keep secrets outside version control.
- Avoid logging credentials and sensitive payment data.

## Inventory integrity

- Use reliable stock reservation and deduction operations.
- Protect against concurrent orders.
- Never silently create or destroy stock.
- Record every adjustment.
- Prevent double-processing.
- Reconcile physical, reserved and available quantities.

## Reliability

- Use queues for expensive/background tasks.
- Implement retries with safeguards.
- Make webhooks idempotent.
- Log failures with actionable context.
- Handle partial external-service outages.

## Compatibility

- Preserve WooCommerce HPOS compatibility.
- Support the relevant WooCommerce product and order editing interfaces.
- Avoid deprecated APIs.
- Keep WordPress and WooCommerce core update-safe.
- Test compatibility with the installed environment.

# 10. IMPLEMENTATION EXECUTION PROTOCOL

Work module by module, using dependency order rather than arbitrary menu order.

For each module:

### Step 1 — Inspect
Determine what already exists.

### Step 2 — Compare
Compare the implementation against the complete functional specification.

### Step 3 — Design
Identify native features, necessary extensions and custom persistence.

### Step 4 — Implement
Write the required production code, database changes and interface extensions.

### Step 5 — Test
Run relevant automated tests and inspect the administrative workflow.

### Step 6 — Verify
Confirm correct permissions, integration behavior, data integrity and compatibility.

### Step 7 — Document
Record implemented features, remaining limitations and relevant architecture decisions.

Then proceed to the next dependency-compatible module.

Avoid stopping after each small change to request approval unless a destructive action, irreversible migration, external expenditure or consequential business-policy decision requires authorization.

Use reasonable non-destructive defaults for implementation details.

Do not silently decide legal, tax, customs or financial policies that require business validation.
